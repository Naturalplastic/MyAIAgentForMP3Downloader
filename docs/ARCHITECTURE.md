# 架构说明

- 文档版本：1.0
- 适用代码版本：`biliagent` 1.0

本文说明系统的整体结构、各层职责及其设计依据。
接口细节见 `DESIGN.md`，代码级说明见 `WALKTHROUGH.md`。

---

## 1. 系统边界

### 1.1 输入与输出

```
输入：自然语言描述
     例如「我想要泠鸢的泼墨漓江，要 mp3 音频」

输出：本地媒体文件 + 文本汇报
     例如 downloads/BV1Ds411h7T1_【泠鸢·原创】泼墨漓江【玖玲】【茜色诗集】.mp3
```

### 1.2 需要 agent 而非脚本的原因

脚本适用于步骤固定的任务。本系统的输入为自然语言，包含若干需要语义判断的环节：

| 输入片段 | 需要的判断 |
|---|---|
| 「泠鸢的泼墨漓江」 | 确定检索词。「泠鸢」为 UP 主名，「泼墨漓江」为作品名，检索时需合并为一个查询 |
| 「那个讲结婚的视频」 | 由主题描述推断具体作品 |
| 「播放量最高的」 | 在候选集合中比较数值字段 |
| 「做成 mp3」 | 识别为两步操作：下载视频、抽取音频 |
| 「帮我下个歌」 | 信息不足，需向用户提问而非假定 |

上述判断无法通过固定规则可靠实现，需要模型参与。而模型只能输出文本，
不执行实际操作，因此需要一层代码负责理解模型输出、执行动作、
并将结果反馈给模型。该层即本系统的 harness。

### 1.3 系统组成

```
┌──────────────────────────────────────────────────────┐
│  harness（本项目实现）                                │
│                                                      │
│   ┌──────────┐   标记协议   ┌──────────────────┐     │
│   │  LLM     │◄────────────►│  agent 循环       │     │
│   └──────────┘              └───┬──────────┬───┘     │
│                                 │          │         │
│                        ┌────────▼──┐  ┌────▼──────┐  │
│                        │ B 站工具   │  │ 媒体工具   │  │
│                        └───────────┘  └───────────┘  │
└──────────────────────────────────────────────────────┘
         │                    │                │
         ▼                    ▼                ▼
   DeepSeek API        B 站 API / CDN    ffmpeg / ffprobe
```

## 2. 分层结构

### 2.1 层次划分

```
L4  入口层        cli.py
L3  循环层        loop.py
    模型适配      llm.py
    协议          protocol.py
    上下文        context.py
    工具调度      tools.py
L2  工具层        bili.py（B 站接口）
                  media.py（本地媒体处理）
L1  会话层        BiliSession
L0  外部依赖      B 站 API、CDN、ffmpeg、DeepSeek API
```

### 2.2 划分依据

分层依据为**变更频率**。同一层内的代码倾向于一起变更；
跨层变更通常意味着抽象层次划分不当。

| 层 | 变更频率 | 变更原因举例 |
|---|---|---|
| L1 | 极低 | HTTP 重试策略、cookie 获取方式 |
| L2 | 中 | B 站接口调整、ffmpeg 参数变更 |
| L3 | 中 | 提示词调整、护栏阈值调整、协议修正 |
| L4 | 高 | 新增命令行参数、输出格式调整 |

### 2.3 依赖方向

依赖方向严格单向：

```
cli.py → loop.py → tools.py → bili.py → 网络
                 ↘ media.py → 子进程
```

约束：

- `bili.py` 仅被 `tools.py` 引用
- `media.py` 仅被 `tools.py` 与 `cli.py` 引用
- `bili.py` 与 `media.py` 之间无依赖
- 无循环依赖

`bili.py` 与 `media.py` 保持独立的原因：两者关注点不同。
`media.py` 只处理本地文件，不涉及网络，可独立测试与复用。

### 2.4 各层职责与禁止事项

| 层 | 职责 | 禁止事项 |
|---|---|---|
| L4 入口 | 参数解析、输出格式化、日志落盘 | 业务判断、网络请求 |
| L3 循环 | 循环控制、护栏、状态管理 | 直接调用外部接口 |
| L3 协议 | 输出解析、指令校验、Schema 定义 | 执行动作 |
| L3 调度 | action 路由、跨轮状态、观察压缩 | 构造 HTTP 请求 |
| L3 上下文 | token 估算、历史压缩 | 修改消息语义 |
| L3 适配 | 模型 API 调用、错误整形 | 协议解析 |
| L2 B 站 | 接口调用、结果清洗、下载 | 音频处理 |
| L2 媒体 | 外部工具探测、媒体处理 | 调用 B 站接口 |
| L1 会话 | cookie、限流、重试、错误分级 | 业务逻辑 |

## 3. 数据流

### 3.1 单轮流程

```
                    ┌─────────────────────────────┐
                    │ messages（模型的全部输入）    │
                    └──────────────┬──────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 1. 上下文预算检查（压缩在调用模型前执行） │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 2. 调用模型，得到文本输出                │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 3. 解析标记                             │
              │    ├─ 格式违规 → 回喂修正指示，重新调用   │
              │    ├─ final_answer → 终止               │
              │    └─ tool_call → 继续                  │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 4. 校验指令（action、参数、取值）        │
              │    └─ 不合法 → 回喂修正指示，重新调用     │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 5. 重复动作检测                         │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 6. 执行工具（含异常兜底）                │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ 7. 压缩结果为观察，追加到 messages        │
              │    成功后重置连续格式违规计数             │
              └────────────────────┬────────────────────┘
                                   │
                                   └────► 返回步骤 1
```

### 3.2 完整的消息序列

以「我想要泠鸢的泼墨漓江，要 mp3 音频」为例，
最终 `messages` 数组包含 11 条消息：

[1]  user         19 字符     原始输入
────────────────────────── 第 1 轮：检索 ──────────────────────────
[2]  assistant    81 字符     <tool_call> search 泠鸢 泼墨漓江
[3]  user       1070 字符     <observation> 5 条候选
────────────────────────── 第 2 轮：下载 ──────────────────────────
[4]  assistant    75 字符     <tool_call> download BV1Ds411h7T1
[5]  user        207 字符     <observation> mp4 15.52 MB
────────────────────────── 第 3 轮：格式纠正 ──────────────────────
[6]  assistant    93 字符     <tool_call> extract_audio（JSON 尾部非法）
[7]  user        150 字符     <system> 格式错误：...（修正指示）
────────────────────────── 第 4 轮：音频抽取 ──────────────────────
[8]  assistant    71 字符     <tool_call> extract_audio mode=mp3
[9]  user        209 字符     <observation> mp3 5.82 MB，校验通过
────────────────────────── 第 5 轮：终止 ──────────────────────────
[10] assistant   119 字符     <final_answer> 任务完成...

完整原文见 `WORKFLOW.md`。

### 3.3 记忆机制

系统的全部状态为 `messages` 数组。此外没有数据库、向量库或外部记忆。
`ToolBox` 中保存的跨轮状态（如 `mp4_path`）属于执行上下文，
不进入模型视野。

## 4. 模型与代码的职责边界

### 4.1 分工原则

模型负责语义判断，代码负责执行与约束。该边界不可模糊：
将约束交由模型决定会导致失控，将判断交由代码则无法处理自然语言。

### 4.2 职责对照

| 事项 | 归属 | 实现位置 |
|---|---|---|
| 确定检索词 | 模型 | — |
| 在候选中选择目标 | 模型 | — |
| 确定音频格式 | 模型 | — |
| 决定是否询问用户 | 模型 | — |
| 判断检索结果是否可信 | 模型 | 依据观察中的 `warning` 字段 |
| 请求限流 | 代码 | `BiliSession._throttle()` |
| 失败重试 | 代码 | `BiliSession._request()` |
| 风控响应处理 | 代码 | `FATAL_HTTP` 集合 |
| 轮数上限 | 代码 | `AgentLoop.run()` |
| 格式违规上限 | 代码 | `AgentLoop.run()` |
| 重复动作上限 | 代码 | `AgentLoop.run()` |
| 磁盘空间检查 | 代码 | `download_html5_mp4()` |
| 产物有效性校验 | 代码 | `_verify_output()` |
| 文件名安全化 | 代码 | `_safe_filename()` |
| 上下文预算 | 代码 | `ContextPolicy.maybe_compress()` |

### 4.3 HTTP 重试不暴露为 action 的原因

若将重试作为模型可调用的工具，模型在遇到失败时会持续调用。
重试属于传输层关注点，其策略（次数、退避、可重试状态码）
应由代码决定。

## 5. 处理不可靠性的机制

### 5.1 问题描述

外部依赖存在无法预先消除的不确定性。系统需要在不确定性之上
为模型提供稳定、可理解的接口。

### 5.2 三种失效模式

#### 模式一：状态码与实际结果不一致

| 来源 | 表现 | 处理 |
|---|---|---|
| B 站 API | HTTP 200，`Content-Type` 正常，错误位于 `data.code` | 显式检查 `code != 0` |
| ffmpeg | 退出码非零，原因位于 stderr | `classify_ffmpeg_error()` 归类为 10 类 |

共同特征：真实错误不在最显眼的状态字段上。
若仅检查 HTTP 状态码或进程退出码，将出现静默错误。

#### 模式二：成功状态下的无效结果

| 情形 | 表现 | 处理 |
|---|---|---|
| 检索无匹配关键词 | `code=0`，`numResults=1000`，内容与关键词无关 | 逐条计算 `relevance`，全部未命中时附加 `warning` |
| WBI 端点未签名 | `code=0`，`message="OK"`，`result=[]` | 不使用该端点 |
| ffmpeg 输出为空 | 退出码 0，文件为 0 字节 | 检查产物大小 |
| ffmpeg 输出损坏 | 退出码 0，文件不可用 | `_verify_output()` 校验容器、音轨、时长 |

共同特征：操作报告成功，但结果不可用。此类失败无异常与错误码，
若不主动校验，系统将输出错误结果并报告成功。

#### 模式三：失败原因难以理解

ffmpeg 的 stderr 包含大量信息，多数与失败原因无关。
将其整体返回会淹没关键信息，完全不返回则模型无从判断。
处理方式为提取关键行并归类，同时保留原始输出尾部。

### 5.3 翻译层

```
外部世界的原始信息                      模型可用的信号
─────────────────────                  ─────────────────────────
HTTP 412                    ─┐
cookie 缺失                  │
ffmpeg stderr（数百行）       ├──────►  {error, message, hint}
moov atom not found          │
data.code = -1200           ─┘
```

该翻译层是 harness 的核心职责。缺少该层时，模型收到的信息
无法用于修正行为。

## 6. 关键设计决策

### 6.1 标记包裹协议

模型每轮输出以下两种形式之一：

```xml
<tool_call>{"action": "...", "args": {...}}</tool_call>
<final_answer>...</final_answer>
```

未采用"尝试解析 JSON，失败即视为最终答复"的原因：
模型输出带前置说明的 JSON 时，整段解析会失败并被误判为最终答复，
导致循环提前结束。

标记包裹使"解析失败"与"它是最终答复"在结构上分离。

### 6.2 观察压缩

工具的原始返回值不直接进入对话，而是经过转换：

| 处理 | 理由 |
|---|---|
| 截断条目数量 | 控制上下文长度 |
| 仅保留必要字段 | 原始检索结果含 30 个以上字段，完整保留使 token 消耗增加约 3 倍 |
| 透传警告字段 | 使模型能识别结果不可信的情形 |

失败结果的字段保留策略与成功结果相反：成功时激进截断，
失败时完整保留。原因是模型依赖失败信息进行修正。

### 6.3 ToolBox 使用实例而非全局变量

跨轮状态保存于 `ToolBox` 实例中。使用全局变量会导致状态不可测试、
无法并行多个会话、问题无法复现。

### 6.4 `chat_fn` 作为唯一模型接口

`AgentLoop` 仅依赖 `chat_fn(messages) -> dict`。
测试时注入 `ScriptedChat`，生产时注入 `DeepSeekClient`，
循环代码无需区分。

该设计使循环逻辑可以与模型的不确定性解耦验证：
出现问题时先运行离线测试，可确定问题位于循环还是模型。

### 6.5 计数器的语义

格式违规计数采用连续语义（成功动作后归零），而非累计语义。

累计语义会将"偶发格式错误但整体推进"的执行判定为失败。
实际曾出现该问题：模型在第 3 轮格式违规、第 4 轮修正成功，
若使用累计计数则会被误判。

累计值单独保存（`total_format_fixes`），用于诊断。

### 6.6 能力探测与双重防护

外部工具能力通过 `probe_capabilities()` 探测，结果用于三处：

| 使用位置 | 方式 |
|---|---|
| 系统提示词 | 告知模型当前可执行的操作范围 |
| 工具守门 | 调用前检查，避免必然失败的执行 |
| 命令行输出 | 供用户查看 |

提示词与工具守门同时生效的原因：仅依靠提示词时模型可能忽略该约束；
仅依靠守门时模型会反复尝试失败的工具调用。
两者结合可在提供信息的同时阻断无效操作。

## 7. 上下文管理

### 7.1 必要性

每轮的观察结果完整进入消息历史。检索的观察约为 1,000 字符。
在五次模型调用的执行中，输入 token 累计 5,533，输出 268，
输入为输出的约 20 倍。

若不控制，长任务将同时面临上下文溢出与成本失控。

### 7.2 压缩策略

```
永久保留：system 提示词
永久保留：原始用户任务
完整保留：最近 3 轮
压缩处理：更早轮次 → 单行摘要
```

保留 system 提示词与原始任务的原因：前者包含协议规则，
后者是目标定义，两者丢失将导致行为异常。

### 7.3 压缩产物的边界

压缩产物本身也需要边界约束。实际开发中依次发现三个问题：

| 问题 | 现象 | 处理 |
|---|---|---|
| 摘要被反复压缩 | 形成嵌套结构，信息层层丢失 | 摘要不再参与压缩 |
| 摘要条数累积 | 每次压缩新增一条，条数线性增长 | 多条摘要合并为一条 |
| 摘要内容增长 | 消息条数受控，但摘要字符数持续增加 | 设置滑窗上限 |

第三个问题的特征值得注意：**消息条数受控不等于上下文受控**。
当时仅检查条数恒定，未检查内容长度。

滑窗生效后的实测数据见 `DESIGN.md` §8.4。

### 7.4 token 估算

估算函数仅用于判断是否需要压缩，不用于计费。
标定过程与精度数据见 `DESIGN.md` §8.2。

系统同时记录 API 返回的真实用量（`usage.prompt_tokens`），
与估算值对照，使偏差成为可测量的问题。

## 8. 中间产物处理

音频抽取以 mp4 为源文件，因此该 mp4 为必要中间产物。
其体积通常为音频的 2~3 倍（实测 15.52 MB 对 5.82 MB）。

### 8.1 清理策略

| 条件 | 行为 |
|---|---|
| 抽取成功且未指定保留 | 删除中间 mp4 |
| 抽取成功且指定保留 | 保留 |
| 抽取失败 | 保留 |

失败时保留的原因：中间文件是唯一的重试依据，删除后需重新下载。

### 8.2 实现约束

| 约束 | 理由 |
|---|---|
| 失败时删除操作不执行 | 保留重试依据 |
| 产物非空才执行删除 | 防止"产物为空但源文件已删" |
| 删除失败不改变成功状态 | 音频已生成，主任务已完成 |

### 8.3 状态一致性

清理完成后将 `ToolBox.mp4_path` 置为 `None`。
若不置空，后续调用会指向已删除的文件。

## 9. 配置管理

### 9.1 加载优先级

```
真实环境变量 > 项目 .env > ~/.biliagent.env
```

环境变量优先级最高的原因：便于临时替换密钥，
无需修改文件。例如：

```bash
DEEPSEEK_API_KEY=sk-xxx python3 -m biliagent.cli agent "..."
```

### 9.2 受管键白名单

仅白名单内的键会从配置文件载入环境变量，
避免无关变量影响运行环境。

### 9.3 脱敏

配置展示命令对密钥做脱敏处理（形如 `sk-49cb…84af`）。
模型适配层在返回错误前移除文本中的密钥。

## 10. 测试结构

### 10.1 层次

| 测试文件 | 项数 | 覆盖范围 |
|---|---:|---|
| `test_env.py` | 55 | 配置解析、优先级、脱敏、布尔开关 |
| `test_tools.py` | 35 | B 站接口、外部工具封装、媒体管线 |
| `test_loop.py` | 116 | 协议解析、指令校验、循环控制、上下文压缩、端到端 |
| `test_llm.py` | 39 | 适配器错误分支、真实 API 冒烟 |

### 10.2 设计要点

**循环逻辑与模型解耦**：`ScriptedChat` 提供预设输出，
使循环验证不依赖模型。问题定位顺序为先运行离线测试，
确定问题位于循环还是模型。

**错误分支使用注入式 mock**：401、402、429、5xx、超时、
非 JSON 响应等路径无法通过反复调用真实 API 覆盖。

**依赖缺失时记为跳过**：媒体管线在无 ffmpeg 或网络时降级为跳过，
而非失败。

**测试 fixture 自建**：媒体管线测试自行合成测试视频，
不依赖目录中既有文件。若依赖既有文件，结果会随运行顺序变化。

**真实 API 调用需显式启用**：由 `--real` 参数控制，避免常规回归产生费用。

## 11. 已知限制

| 项 | 说明 |
|---|---|
| 音质 | 游客身份下 DASH 音频轨上限 187 kbps；当前实现使用 html5 变体 |
| 画质 | 上限 360P |
| 签名 URL | 有时效，本项目持久化 `bvid` / `cid` 而非 URL |
| 频率边界 | 未测试风控阈值 |
| 长会话 | 稳定性验证至 6 轮 |
| 流式输出 | 未实现 |
| 并发 | 单会话串行，未实现多任务并行 |
| 测试估算精度 | token 估算误差范围 0.67–1.30 |
